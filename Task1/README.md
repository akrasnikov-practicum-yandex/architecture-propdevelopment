# Задание 1. Проверочный лист по безопасности данных PropDevelopment

## 1. Контекст и объём проверки

PropDevelopment готовится к комплексному аудиту информационной безопасности. Из [описания системы](../docs/description.md) выделяются ключевые «болевые точки», ради которых аудит и инициирован:

- внутренние потоки данных между IT-продуктами не контролируются системно;
- API партнёров (управляющих компаний) предоставляют доступ к ПДн без единых политик; **партнёр одной УК может видеть/менять данные клиентов другой УК**;
- в личном кабинете клиента иногда отображаются данные другого клиента — реальный инцидент нарушения изоляции;
- один специалист по ИБ на всю компанию + сорванная коммуникация между командами после ротации руководителей;
- неуверенность в соответствии требованиям ФЗ-152;
- недавняя громкая утечка у конкурента в СМИ — давление со стороны руководства.

**Цель проверочного листа** — выполнить первый шаг аудита (определение целей и объёма + сбор данных по [методологии](../docs/IB.md#i-управление-доступом)): инвентаризировать данные компании, классифицировать их по стандартам **ISO/IEC 27001** и **ISO/IEC 27002**, оценить релевантные риски и обосновать оценки. Результат служит входом для следующих шагов: ранжирование угроз, формирование плана улучшений, исполнение и мониторинг.

**Объём:** все типы данных, обрабатываемые в четырёх доменах PropDevelopment — *Продажи*, *ЖКУ*, *Финансы*, *Дата*. Архитектурный контекст — [c4-company.png](../docs/c4-company.png).

## 2. Методология

### Стандарты

Применяется классификация **ISO/IEC 27001/27002** на 4 категории по уровню чувствительности:

| Категория | Определение | Принцип защиты |
|---|---|---|
| **Публичные** | Информация без ограничений распространения. Свободная циркуляция не угрожает компании. | Защита целостности и доступности (но не конфиденциальности) |
| **Внутренние** | Информация для внутреннего использования. | Контроль доступа сотрудников, защита от внешнего разглашения |
| **Конфиденциальные** | Высокая ценность, ограничено распространение. ПДн, коммерческая тайна, финансовые данные. | Шифрование, минимальные привилегии, журналирование, маркировка |
| **Секретные** | Утечка ведёт к серьёзнейшим последствиям или нарушению закона. Платёжные данные, ключи, привилегированный доступ. | Изолированные хранилища (HSM, vault), ротация, MFA, строжайший аудит |

Для конфиденциальных данных дополнительно учитываются требования **ФЗ-152 «О персональных данных»**.

### Виды рисков (по ТЗ)

Каждый тип данных оценивается по пяти видам рисков:

- **Утечка** — несанкционированный доступ, разглашение третьим лицам.
- **Потеря** — безвозвратная недоступность (отказ хранилища, отсутствие/повреждение бэкапов).
- **Искажение** — несанкционированное или ошибочное изменение, нарушение целостности.
- **Некачественные данные** — ошибки сбора, неполнота, рассогласованность форматов.
- **Обесценивание** — потеря актуальности/ценности со временем.

### Шкала оценок

| Оценка | Критерий |
|---|---|
| 🟢 **Незначительный** | Реализация риска не вызывает заметных последствий — либо риск не применим к данной категории, либо ущерб локальный и легко устраним |
| 🟡 **Значительный** | Реализация риска приводит к ощутимым последствиям: операционные сбои, репутационные потери, расходы на устранение, недовольство клиентов |
| 🔴 **Критический** | Реализация риска приводит к нарушению законодательства, прямым финансовым потерям крупного масштаба, юридическим спорам, риску для физической безопасности или блокировке бизнеса |

| Обесценивание | 🟢 | Описания живут до сдачи объекта и регулярно актуализируются |

| Искажение | 🟡 | Неверные цены и контакты ведут к жалобам и нарушениям прав потребителей |

| Некачественные | 🟢 | Формат ключей определяется провайдером, на стороне клиента не варьируется |
| Обесценивание | 🟡 | Просроченные ключи ломают доступ; необходима регулярная ротация |

#### SC-2. Учётные данные БД и сервисные учётки

| Риск | Оценка | Обоснование |
|---|---|---|
| Утечка | 🔴 | Прямой доступ ко всем данным компании, включая ПДн и финансы |
| Потеря | 🔴 | Недоступность приложений до восстановления учётных данных из защищённого хранилища |
| Искажение | 🟡 | Повреждение строк подключения = отказ сервиса (легко детектируется) |
| Некачественные | 🟢 | Формат учётных данных стандартизован |
| Обесценивание | 🟡 | Пароли требуют регулярной ротации; старые пароли = «мёртвые» доступы и риск |

#### SC-3. TLS-сертификаты и приватные ключи шифрования

| Риск | Оценка | Обоснование |
|---|---|---|
| Утечка | 🔴 | Компрометация TLS = MitM-атаки, расшифровка трафика, подделка идентичности компании |
| Потеря | 🔴 | Без приватных ключей невозможно расшифровать защищённое хранилище данных |
| Искажение | 🔴 | Изменение ключей делает зашифрованные данные нечитаемыми навсегда |
| Некачественные | 🟢 | Формат ключей и сертификатов стандартизован |
| Обесценивание | 🟡 | Истёкшие сертификаты ломают TLS на сервисах, требуется регулярное обновление |

#### SC-4. Учётные записи администраторов и привилегированный доступ

| Риск | Оценка | Обоснование |
|---|---|---|
| Утечка | 🔴 | Полный административный контроль над инфраструктурой компании |
| Потеря | 🟡 | Восстановимо через резервных администраторов и процедуры break-glass |
| Искажение | 🔴 | Повреждение прав = отказ оператора в управлении системами |
| Некачественные | 🟢 | Учётные записи и роли строго регламентированы |
| Обесценивание | 🟡 | **Учётки уволенных сотрудников опасны** — описание системы прямо указывает на отсутствие автоматического отзыва |

## 6. Приоритизация и выводы

**Зоны критического риска (🔴), требующие немедленного внимания:**

1. **Изоляция данных собственников и партнёрских интеграций** (CN-3, CN-8) — есть подтверждённые инциденты пересечения данных между клиентами и между УК. Прямое нарушение ФЗ-152 и архитектурный дефект разграничения.
2. **Защита всего пула финансовых и сделочных данных** (CN-2, CN-4, CN-5, CN-6) — все 3 первых риска (утечка/потеря/искажение) — критические; ущерб одновременно юридический, финансовый и репутационный.
3. **Управление секретами** (SC-1..SC-4) — утечка ключей или БД-учёток компрометирует всю компанию. Учётки уволенных сотрудников остаются активными.
4. **Безопасность «Умного дома»** (CN-7) — искажение/утечка переходит в физическую угрозу, что выводит риск за рамки информационной безопасности.
5. **Защита логов и конфигураций инфраструктуры** (IN-3, IN-4) — единственные критические оценки во внутренней категории, без них невозможен корректный аудит.

**Эти зоны определяют объём проверки на следующих этапах аудита** — управление доступом, шифрование данных, защита инфраструктуры, реагирование на инциденты — детальный чек-лист вопросов см. в [docs/IB.md](../docs/IB.md).
