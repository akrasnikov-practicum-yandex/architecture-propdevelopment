# Проверочный лист безопасности бизнес-систем PropDevelopment

## 1. Объём проверки и определение «бизнес-систем»

Под бизнес-системами понимаются все IT-продукты, обеспечивающие операционную деятельность PropDevelopment, в четырёх архитектурных доменах ([docs/description.md](../docs/description.md), [docs/c4-company.png](../docs/c4-company.png)):

- **Продажи:** витрина продаж, `client-tour-app`, `client-mart-app`, `client-crm-app`, `client-mart-estate-app` + их БД.
- **ЖКУ:** витрина для собственников, `tenant-core-app`, CRM собственников + БД.
- **Финансы:** `accountant-service-1`, служба каталогов + БД.
- **Дата:** хранилище, BI, отчётность.
- **Внешние интеграции:** госорганы (Росреестр, ЕГРН) для онлайн-сделок; API партнёров — управляющих компаний (УК); платёжные шлюзы.
- **Канал собственников:** мобильное приложение с подключением к «Умному дому» (управление замком квартиры, автоматика этажа).

Чисто инфраструктурные элементы (приватное облако, ЦОД, гибридные мощности, межсетевой экран) включаются в проверку в той части, в которой они обслуживают перечисленные бизнес-системы.

## 2. Связь с проверочным листом по данным (Task 1)

Все коды типов данных (PD-*, IN-*, CN-*, SC-*) и оценки рисков (🟢 / 🟡 / 🔴) — из Task 1: [Task1/README.md](../Task1/README.md), [Task1/data_security_mindmap.drawio](../Task1/data_security_mindmap.drawio). Краткая легенда:

| Префикс | Категория ISO/IEC 27001 |
|---|---|
| **PD-*** | Публичные данные (описания объектов, маркетинг) |
| **IN-*** | Внутренние данные (планы зданий, ремонты, логи, конфиги, BI) |
| **CN-*** | Конфиденциальные данные (ПДн клиентов и собственников, договоры, финансы, госорганы, «Умный дом», API УК) |
| **SC-*** | Секретные данные (API-ключи, БД-учётки, TLS-ключи, привилегии админов) |

В комментариях к вопросам ниже ссылки на эти коды показывают, какие именно типы данных находятся под угрозой при отрицательном ответе.

Сохранены все 5 разделов шаблона [docs/IB.md](../docs/IB.md) — каждый закрывает конкретную проблему компании, описанную в [description.md](../docs/description.md). Дополнительно добавлена подсекция **V.3 «Интеграции с партнёрами (УК) и API M2M»** — уникальная для PropDevelopment пробоина, не покрытая базовым шаблоном.

| Раздел | Зачем нужен PropDevelopment | Критические данные из Task 1 |
|---|---|---|
| **I. Управление доступом** | Партнёр одной УК может видеть/менять данные клиентов другой; в личном кабинете клиента отображаются чужие ФИО — нарушены принципы минимальных привилегий и тенант-изоляции. Один ИБ-специалист на компанию + ротация руководителей IT → нет уверенности в управлении учётками уволенных. | CN-3, CN-8 (🔴 утечка), SC-4 (🔴 утечка) |
| **II. Безопасность данных** | Главная декларируемая проблема: «нарушен контроль данных», нет системных ограничений на потоки между IT-продуктами, контракты API передают ПДн без необходимости, нет уверенности в соответствии ФЗ-152, у конкурента — публичная утечка в СМИ. Развитие BI/ML/AI заблокировано отсутствием Data Governance. | CN-1..CN-6 (🔴 утечка/искажение), SC-1..SC-3 |
| **III. Защита инфраструктуры** | Гибридная среда: собственный ЦОД + приватное облако + арендованные мощности у провайдера. Сегментация и сетевой контроль внутри среды не описаны. IN-4 (карта инфраструктуры) — единственная критическая утечка в категории «Внутренние данные». | IN-3, IN-4 |
| **IV. Управление инцидентами** | Жалобы клиентов на отображение чужих данных в ЛК не расследованы до конца. Громкая утечка у конкурента — триггер аудита. | **V. Специфические аспекты** | Мобильное приложение собственников + «Умный дом» (CN-7 — переход в физическую угрозу при компрометации); собственный ЦОД с физическим доступом; гибридное облако с арендованными мощностями. **V.3 — отдельный фокус на партнёрских API**: системы УК интегрированы без единых политик безопасности и контроля передаваемых данных. | CN-7, CN-8, SC-1 |

## 4. Проверочный лист

Условные обозначения в графе «Да/Нет»:
- **Да** — есть прямое подтверждение в [description.md](../docs/description.md) или архитектуре.
- **Нет** — прямо описанное нарушение либо отсутствие практики.
- **Частично** — есть лишь часть требуемого (например, периметр защищён, но внутри сегментации нет).
- **В процессе** — работа начата (например, классификация данных в Task 1).
- **Требует проверки** — данных в описании недостаточно; вопрос — рабочая точка для следующего шага аудита.

| 13  | Применяются ли средства для отзыва прав доступа? | Требует проверки | Не описано. Критично для оперативного отзыва доступа уволенных и скомпрометированных учёток (SC-4). |

| 1   | Используется ли система мониторинга безопасности (SIEM) для корреляции событий и анализа аномалий в режиме реального времени? | Нет | SIEM в описании не упомянут. Без него невозможно своевременно обнаруживать инциденты типа «отображение чужих данных в ЛК» (CN-3 🔴). Рекомендация — Splunk / IBM QRadar / Solar Dozor. |
| 2   | Настроены ли автоматические оповещения об инцидентах и подозрительной активности (например, попытках несанкционированного доступа)? | Нет | Жалобы клиентов на чужие данные «иногда могут отображаться» — то есть инциденты обнаруживаются клиентами, а не системой. Алертинга нет. |
| 3   | Разработан ли план реагирования на инциденты, включающий анализ, эскалацию и восстановление системы? Проводится ли обучение сотрудников? | Нет | Один ИБ-специалист на всю компанию + сорванная коммуникация после ротации руководителей → ни runbook'ов, ни обучения сотрудников. Учитывая случай конкурента в СМИ — это блокирующий пункт. |
| 4   | Проводятся ли симуляции инцидентов (учения) для проверки готовности сотрудников к реагированию на кибератаки? | Требует проверки | Не упомянуто. Минимум — tabletop-учения по сценариям утечки CN-* и компрометации SC-*. |
| 5   | Ведётся ли статистика по всем зарегистрированным инцидентам и используются ли результаты анализа для корректировки политики безопасности? | Нет | Жалобы клиентов в ЛК остаются нерасследованными до конца — нет ни регистрации, ни анализа. |
| 6   | Как часто проводятся внутренние и внешние аудиты безопасности? Обновляются ли политики и процедуры на основе результатов этих аудитов? | Нет | Готовится первый комплексный аудит — до этого регулярных аудитов не было. По результатам должен быть запущен периодический процесс (минимум раз в год + при значительных архитектурных изменениях). |

Мобильное приложение собственников — B2C, MDM не применим, но обязательны device attestation, биометрия и защищённое хранилище токенов на устройстве (CN-7 🔴 «Умный дом»). |

| 3   | Проводится ли автоматическое выявление и ограничение использования незарегистрированных или неавторизованных устройств в сети? | Требует проверки | NAC-решения (Network Access Control) не упомянуты. |

#### V.3. Интеграции с партнёрами (УК) и API M2M ⭐ новый раздел

Включён в проверочный лист потому, что описание прямо называет проблемы партнёрских API одной из двух главных болевых точек компании наряду с контролем данных. Базовый шаблон IB.md не покрывает M2M-интеграции, поэтому раздел добавлен.

| №   | Вопрос | Да/нет | Комментарий |
| --- | --- | --- | --- |
| 1   | Используется ли единый API Gateway с авторизацией M2M-трафика для всех интеграций с партнёрами и госорганами? | Нет | «Системы PropDevelopment используют API управляющих компаний без единых политик по безопасности и без системного контроля за передаваемыми данными». Единого Gateway нет → CN-8 (🔴) и CN-6 (🔴 интеграции с госорганами) не защищены централизованно. |
| 2   | Применяется ли mTLS / OAuth2 client_credentials для аутентификации партнёрских систем? | Требует проверки | Не описано. Базовый минимум — mTLS + ротация client-secret через Vault (SC-1 🔴). Без этого риск компрометации одного партнёра распространяется на всю экосистему. |
| 3   | Реализовано ли строгое разграничение тенантов (УК) в API партнёров? | Нет | «Партнёр из одной управляющей компании может увидеть или изменить данные клиентов и жилищных комплексов, которые относятся к другой компании» — реализованная угроза CN-8 (🔴), нарушение модели мультитенантности. |
| 4   | Проводится ли формальный security-review API-контрактов перед вводом в эксплуатацию? Минимизируются ли передаваемые ПДн? | Нет | «Контракты API содержат категории данных, которые явно предоставляют персональные данные» — то есть требование «передавать только необходимое» нарушено. Нужен процесс security-review каждого нового контракта + DLP-проверка трафика на ПДн. |
| 5   | Ведётся ли аудит обращений партнёров (логирование, корреляция в SIEM, rate limiting, anomaly detection)? | Требует проверки | Не описано. Связан с IV.1 (SIEM нет) и IN-3 (логи). Минимум — детальный access log на API Gateway с прокидыванием в SIEM, rate limiting per-tenant, оповещения на аномальные паттерны (массовый выгруз, доступ к чужому tenant ID). |

## 5. Приоритизация дальнейших шагов

Зоны, требующие немедленного действия по результатам проверочного листа (упорядочены по влиянию на главные критические данные из Task 1):

1. **Тенант-изоляция в партнёрских API и личном кабинете клиента** (I.4, I.7, I.10, II.7, II.11, V.3.1, V.3.3) — устранить реализованные угрозы CN-3 и CN-8. Ввести API Gateway, ABAC с тенант-атрибутами, security-review контрактов.
2. **Управление секретами и доступом к БД** (I.1, I.3, I.5, II.3) — внедрить Vault/HSM, MFA для админов, автоотзыв учёток, ротацию ключей. Защищает SC-1..SC-4.
3. **Шифрование и сетевая изоляция** (II.2, III.2, III.11) — TLS/mTLS внутри среды, NetworkPolicies, сегментация по доменам. Защищает все CN-* и IN-4.
4. **SIEM, IDS/IPS и план реагирования на инциденты** (IV.1–IV.3, IV.5, V.3.5) — дать ИБ-специалисту инструменты и процессы для обнаружения и расследования инцидентов; зафиксировать runbook'и.
5. **Data Governance и формальная политика классификации** (II.1, II.7, II.8, II.9, II.13) — финализировать классификацию из Task 1, ввести метки, DLP, разблокировать BI/ML-инициативы.
6. **Регулярные аудиты и обучение** (IV.4, IV.6) — превратить разовый аудит в постоянный процесс с tabletop-учениями.
