# Требования к внешним интеграциям — Платформа партнёра «Умный дом»

## 1. Требования к безопасности

### 1.1 Шифрование и защита канала
- Все взаимодействия между PropDevelopment и платформой партнёра должны проходить исключительно по защищённому каналу связи **TLS 1.3** (TLS 1.2 — как минимально допустимый fallback).
- Использовать только надёжные Cipher Suites (запрет RC4, DES, 3DES, EXPORT-шифров).
- Сертификаты партнёра должны быть выпущены доверенным CA и регулярно обновляться (срок действия не более 1 года). Использовать Certificate Pinning для критичных M2M-соединений.

### 1.2 Биометрические данные (лицо)
- Изображения лиц и биометрические шаблоны — **специальная категория персональных данных** по **ФЗ-152 «О персональных данных», ст. 11**.
- Обработка биометрии допустима только **на основании явного письменного согласия субъекта ПДн** (ст. 9 ФЗ-152). Согласие хранится в PropDevelopment (tenant-crm).
- Партнёр **обязан** иметь статус оператора ПДн и выполнять требования ФЗ-152 в части хранения и обработки биометрии.
- Биометрические шаблоны хранятся только на стороне партнёра. PropDevelopment хранит лишь идентификатор пользователя и флаг наличия согласия.
- Передача изображений лица от мобильного приложения к партнёру допустима только в зашифрованном виде и исключительно с целью регистрации биометрии.

### 1.3 Государственные номера автомобилей
- Государственный регистрационный номер транспортного средства — **персональные данные** в понимании ФЗ-152 (позволяет идентифицировать физическое лицо через базу ГИБДД).
- Номера автомобилей хранить в **зашифрованном** виде (AES-256) в базе данных PropDevelopment (smart-home DB).
- Партнёру передавать номера только для целей управления доступом (въезд/выезд на территорию). Запрещено использование этих данных партнёром в иных целях.

### 1.4 Минимизация данных
- Партнёру передаются только минимально необходимые данные. Запрещено включать в API-контракты поля ФИО, адреса, паспортные данные, если они не нужны для работы функции.
- API-контракты (Swagger/OpenAPI) проходят проверку **отдела ИБ** перед внедрением и после каждого обновления. Проверяется: избыточность полей, возможность IDOR-атак (доступ к данным другого клиента).

### 1.5 Сетевая безопасность (Network Security)
- Исходящие запросы к API партнёра проходят через **API Gateway** PropDevelopment. Прямые запросы из мобильного приложения к платформе партнёра **запрещены**.
- Исходящий трафик к партнёру отправляется с фиксированных белых IP-адресов PropDevelopment (NAT/Proxy шлюз).
- Входящие вебхуки от партнёра принимаются **только** от известных IP-пулов партнёра, прошедших валидацию на Firewall.

### 1.6 Webhook-безопасность
- Все входящие вебхуки от партнёра должны содержать **HMAC-SHA256 подпись** в заголовке запроса.
- PropDevelopment (Smart Home Adapter) **обязан** проверять подпись до обработки события. Вебхуки с некорректной подписью отклоняются с HTTP 401.
- Секрет для HMAC генерируется при onboarding-е партнёра и хранится в Vault. Ротация секрета — не реже 1 раза в 6 месяцев.

### 1.7 Аудит-лог
- Каждое событие открытия двери домофона или шлагбаума **должно логироваться** в smart-home DB: кто инициировал (user_id или «авто»), какое устройство, timestamp, тип события (биометрия / номер / ручное открытие).
- Журнал событий доступа хранится **не менее 1 года** и доступен для проверки отделом ИБ.
- Доступ к журналу ограничен ролями безопасности (Security Officer, Auditor).

## 2. Протоколы аутентификации и авторизации

### 2.1 Межсервисное взаимодействие (M2M: PropDev → Партнёр)
- Авторизация сервер-сервер: **OAuth 2.0 (Client Credentials Flow)**.
- Альтернатива для повышенной безопасности: **Mutual TLS (mTLS)** — взаимная проверка клиентского и серверного сертификатов.
- Access Token имеет срок жизни ≤ 1 час. Обновление — через refresh или повторный CC-запрос.
- Client ID и Client Secret хранятся в Vault (HashiCorp Vault или аналог). Ротация — не реже 1 раза в 3 месяца.

### 2.2 Пользовательская авторизация в Mobile App
- Мобильное приложение аутентифицирует пользователя в системах PropDevelopment по **OpenID Connect (OIDC)**.
- Команды управления устройствами мобильное приложение передаёт на Smart Home Adapter с **JWT Bearer Token** (выдаётся PropDevelopment IdP, срок жизни ≤ 15 минут).
- Мобильное приложение **не получает** токены доступа к платформе партнёра. Всё взаимодействие с партнёром — исключительно через Smart Home Adapter.

### 2.3 Авторизация на стороне партнёра
- Партнёр должен проверять, что запрос исходит только от PropDevelopment (по Client ID / Client Certificate).
- Партнёр не должен принимать запросы управления устройствами из других источников.

## 3. Взаимодействие между системами

### 3.1 Синхронное взаимодействие (команды)
- Ручное открытие домофона/шлагбаума из мобильного приложения: **REST API (HTTPS)**, синхронный ответ.
- Маршрут: Mobile App → Smart Home Adapter → API Gateway → Платформа партнёра.
- Таймаут команды открытия устройства: **5 секунд**. При превышении — ошибка с понятным сообщением пользователю.

### 3.2 Асинхронное взаимодействие (события)
- События от платформы партнёра (звонок домофона, проезд через шлагбаум, тревога): **Webhooks** → API Gateway → Smart Home Adapter.
- Для критичных событий (тревога, нераспознанный человек) допустимо использование брокера сообщений (**Kafka**) для гарантированной доставки.
- Smart Home Adapter маршрутизирует события в tenant-core-app для отображения уведомлений в Mobile App.

### 3.3 Синхронизация прав доступа
- При добавлении/удалении автомобиля собственника или изменении биометрических прав — Smart Home Adapter **синхронизирует** актуальный список с платформой партнёра в течение **5 минут**.
- Удаление собственника из системы PropDevelopment → автоматическая инициация отзыва биометрии и прав доступа у партнёра.

### 3.4 Контракты API
- Все API-контракты описываются в **Swagger/OpenAPI 3.0** и проходят проверку отдела ИБ перед внедрением.
- Версионирование API: семантическое (v1, v2). Breaking changes — только с уведомлением за 30 дней.
- Партнёр предоставляет Sandbox-среду для тестирования интеграции.

## 4. SLA и операционные требования

| Параметр | Требование |
|---|---|
| Доступность API партнёра | ≥ 99.5% в месяц (критичный сервис безопасности ЖК) |
| Время отклика команды открытия | < 3 секунды (p95) |
| Время доставки вебхука от события | < 10 секунд (p95) |
| Уведомление о плановых работах | За 48 часов |
| Уведомление о незапланированных инцидентах | За 2 часа |
| Время устранения критичного инцидента | ≤ 4 часа |
| Уведомление PropDevelopment об инциденте безопасности у партнёра | В течение 4 часов |
| Отзыв ключей/токенов при расторжении договора | В течение 24 часов |

- Партнёр обязан предоставить **Status Page** для мониторинга доступности своей платформы.
- Режим деградации: при недоступности платформы партнёра домофоны и шлагбаумы должны работать в **автономном режиме** (офлайн-кэш разрешённых доступов на устройстве).

## 5. Соответствие законодательству

### 5.1 Федеральный закон № 152-ФЗ «О персональных данных»
- Биометрические данные (фото лица, шаблон) и государственные номера автомобилей — **персональные данные**. Биометрия — специальная категория ПДн (ст. 11 ФЗ-152).
- Обработка ПДн допустима только на основании **согласия субъекта** (ст. 9). Форма согласия хранится в tenant-crm и доступна субъекту по запросу.
- Субъект вправе **отозвать согласие** в любой момент. После отзыва:
  - биометрия удаляется у партнёра в течение **5 рабочих дней**;
  - данные об автомобиле удаляются из системы PropDevelopment в течение 30 дней.
- Партнёр обязан подтвердить своё соответствие ФЗ-152 (наличие уведомления в Роскомнадзор).

### 5.2 Локализация данных (ст. 18.1 ФЗ-152)
- Хранение ПДн граждан РФ — **только на территории Российской Федерации**.
- Партнёр обязан письменно подтвердить, что все серверы, на которых хранятся ПДн российских граждан (биометрия, номера авто), расположены на территории РФ.
- PropDevelopment вправе провести аудит размещения инфраструктуры партнёра.

### 5.3 Право субъекта на удаление данных
- Собственник вправе потребовать удаления всех своих данных из системы партнёра через интерфейс PropDevelopment.
- Партнёр обязан исполнить запрос на удаление в течение **30 дней** с момента получения и предоставить подтверждение.

### 5.4 Договорная база
- Интеграция оформляется **договором об обработке ПДн** (DPA) с партнёром, включающим: перечень передаваемых данных, цели обработки, сроки хранения, меры защиты.
- Партнёр несёт ответственность за инциденты, произошедшие по его вине (утечка биометрии, НСД).
